# ワークスペース＝ブランド＝会社＝組織：定義と実装の整合整理

ユーザー定義（2026-09-22）：**「ワークスペース＝ブランド＝会社＝組織」＝これらは単一の概念**（入れ子ではない）。
本書は、この定義に対して現状の実装・設計にある矛盾を洗い出したもの。行番号は `spot-app/index.html`、スキーマは `supabase/migrations/`。

---

## 1. 現状のデータモデル（実装されているもの）

| 概念 | 実体 | 備考 |
|---|---|---|
| ワークスペース | `organizations` 行 | 1ユーザーが**所有できるのは生涯1つ**（サインアップ時に作られる） |
| 個人/組織の別 | `organizations.is_personal` (bool) ＋ signup の `account_type` | 個人=is_personal:true・人名／組織=false・会社名 |
| ブランド | `brands` 子テーブル（org_id 紐づけ） | UI上は **org あたり1件のみ**（`.limit(1).maybeSingle()`） |
| 会社名 | `organizations.name` | |
| ブランドロゴ | `brands.assets.logo` | 別テーブル |
| プラン特典 | `plans.brands` 列（1=既定, 0=無制限） | 料金表に「複数ブランド管理／ブランド無制限」表示 |

**org 作成経路**：`handle_new_user`（サインアップ時1つ）／`complete_onboarding`（OAuth時 個人WS→会社WS転換）／個人→組織アップグレード（**既存WSの転換**、新規作成ではない）。
→ **ユーザー向けの「新しいワークスペースを作る」フロー・RPC は存在しない**（`create_organization` 無し）。追加所属は招待経由の“参加”のみ。

## 2. 定義との矛盾（5点）

### C1. `brands` が別テーブル＝同一アイデンティティの二重管理
workspace=brand なら **org 自身がブランド**。だが実装は会社名=`org.name`／ロゴ=`brands.assets.logo` と**1つのアイデンティティが2テーブルに分裂**。会社プロフィール画面（`view-settings` 2315-2351）は両者を1つとして編集するので **UIの意図は「workspace=brand」に一致**するが、**ストレージ構造が定義と不整合**。

### C2. 個人/組織の二分が「単一概念」に反する
`account_type`(personal/org)・`is_personal` で workspace を2種に分岐。
- 個人WS＝ブランド無し・人名・**会社プロフィール非表示**（5222）。
- 組織WS＝ブランド有り・会社名。
定義上は個人WSも1つのブランド/会社のはずだが、**個人WSはブランド識別（名前+ロゴ）を持てない**。切替UIも個人を `L('Personal','個人')`（2865）と“会社でないもの”として表示。

### C3. 「複数ブランド管理」がどの解釈でも未提供
- 解釈A（1 org に複数 brand）：UIは単一ブランドのみ＝未提供。
- 解釈B（複数ワークスペース＝複数ブランド）：**新規ワークスペース作成が不可**（所有は生涯1つ）＝未提供。
`plans.brands` 列＋料金表「複数ブランド管理／ブランド無制限」(5804) は**どちらの意味でも実装が無い**（現状 `soon:true` の「近日」で正直化）。

### C4. 「ワークスペースを追加する」ボタンが機能しない
アカウントメニューに「ワークスペースを追加する」(1714)。だが押下ハンドラ(3003)は **設定へ遷移＋トーストのみで、何も作らない**。定義（複数WSを持てる）を示唆するUIだが裏付けが無い＝デッドエンド。

### C5. 用語が不統一
UI文字列の出現数：**ワークスペース48／会社49／組織46／ブランド10**。定義上は同一概念だが、4語を場面ごとに使い分けており、ユーザーが「別物」と誤解しうる。単一概念なら主要語を1つに統一すべき。

## 3. 整合の方向（2案）

### 案X：workspace=brand に一本化（ユーザー定義に合わせる）＝推奨
- `brands` テーブルを廃し、ブランド情報（ロゴ等）を `organizations`（例：`organizations.assets`）に統合。
- 個人/組織の区別を「表示名が人名か会社名か」程度に緩め、**どのWSもブランド識別（名前＋ロゴ）を持てる**ように。
- **「複数ブランド」＝複数ワークスペースの新規作成フロー**を提供（`create_organization` RPC＋UI）。`plans.brands` を作成上限として実効化。
- 「ワークスペースを追加する」を本物にする。
- 用語を **「ワークスペース」（または「ブランド」）に統一**。
- 影響：スキーマ移行（brands→org統合）、作成フロー新設、用語一括置換。大きめだが定義と一致。

### 案Y：現状構造を維持し、定義/文言側を調整
- `brands` 子テーブル維持。「複数ブランド管理」は 1 org 内の複数brand UI として実装（or 恒久「近日」）。
- workspace ≠ brand（brandはorg内の下位概念）と**定義を修正**。
- 用語は現状の使い分けを明文化。
- 影響：小さいが、ユーザーの明言（workspace=brand）とは食い違う。

---

## 4. 要判断
- **案X（定義に一本化）／案Y（構造維持・定義調整）どちらで進めるか。**
- 案Xなら追加で：複数ワークスペース所有を許すか（＝複数ブランドの本質）／個人WSもブランド化するか／用語の統一先（ワークスペース or ブランド）。
